## 结论和边界

1. 没有 key、正文逐字节相同，也出现 **21,084 ↔ 21,112**。所以 key 不是这一输入计量变化的必要条件。不能据此证明输入量增加来自特定 tokenizer、隐藏提示、服务端计费错误或路由机制。
2. 相同正文、同一本机连接，仍出现 **0 → 99.43% → 0 → 0**，第二和第三次请求开始只隔约 5.81 秒。本批不能用客户端正文改写或重新 TLS 连接解释高命中后归零；上游缓存分配、请求处理和用量转发仍待核验。
3. 第一次不是已证明的冷缓存：本批复用了上一批的合成前缀。第二次高命中也不证明第三次理应使用同一个上游缓存。只有四个响应，不能从两种计量值推断恰好存在两个后台节点。
4. 本批是精确 replay，没有正式 Agent 的真实回复、reasoning、工具循环或 append 增长；`completed=true` 只表示四个受控响应完成，`input_tokens_stable=false` 才表示计量结果不稳定。本批没有带 key 的比较组，不能据此判断 key 有效或无效。

**下一步可以单独验证固定 key 的四次精确重放**，保持现有正文和选项，只增加同一个 key，并把每个响应的输入量与缓存量分别作为观测。由于无 key 的计量本身会变化，不能再用一对请求输入量不等直接归因于 key；也不能把跨批结果当作充分的因果比较。更严格的 key 效果验收仍需同时间段交替重复的两臂与稳定控制，并在分析前明确处理输入差异的规则。
